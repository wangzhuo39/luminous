# Luminous 前端产品分层与结构调整指导 v1

> 适用目录：`apps/companion-web/companion-ui/`
>
> 目标：不删除功能，只调整功能优先级、入口层级和代码归属，让前端更像长期陪伴产品，而不是功能并列的拼盘。

## 1. 背景

当前前端已经具备完整骨架：

- 主场景陪伴与对话
- Today / Timeline
- 来信、记忆、隐私
- 任务、习惯、活动、日记、提醒、日历
- PWA、离线壳、深链、草稿恢复

问题不在“有没有功能”，而在“哪些功能先出现、哪些功能后展开、代码应按什么产品语义组织”。

## 2. 产品层级

### 2.1 第一层：主场景

主场景只承载三件事：

- 陪伴者在场
- 最近回应可见
- 用户可以立即开口

主场景不应被任务、日历、日记等操作感过强的内容抢走注意力。

### 2.2 第二层：一级辅助空间

一级辅助空间是产品的“近处物件”，应在首屏或一级覆盖层中可达：

- Today
- 来信
- 记忆
- 隐私

它们的职责分别是：

- Today：照看今天
- 来信：低打扰主动联系
- 记忆：看见“为什么记得”
- 隐私：通知、DND、边界与保存策略

### 2.3 第三层：二级能力

二级能力是“今天里面再展开的事情”，不应作为首屏主视觉：

- 任务
- 习惯
- 活动
- 日记
- 提醒
- 日历

这些能力要保留，但应藏在 Today 或相关子视图中，作为支持长期生活流的工具，而不是首页第一层入口。

### 2.4 第四层：产品化底座

这一层只负责产品可用性，不抢体验叙事：

- PWA 安装
- 更新提示
- 离线壳
- 草稿恢复
- 空间级深链

### 2.5 不变项

- 训练底座不进入前端首屏判断
- 不新增第二个首页
- 不引入框架式重构来掩盖层级问题

## 3. 入口与视觉顺序

建议的视觉顺序是：

1. 陪伴者与对话
2. Today
3. 来信
4. 记忆
5. 隐私
6. 任务 / 习惯 / 活动 / 日记 / 提醒 / 日历

其中第 1 到第 4 项应能构成“看起来已经足够完整”的产品第一印象。

对 Today 覆盖层的要求是：

- 先摘要，后 Timeline
- 先一级概览，后二级能力
- 二级能力必须是显式展开，不是默认等权平铺

## 4. 代码结构原则

当前顶层按文件类型分目录是合理的：

- `assets/`
- `styles/`
- `js/`

需要调整的是 `js/` 内部组织方式。它不应继续主要按技术文件类型散放，而应按产品层级和能力域组织。

### 4.1 结构目标

建议的目标方向是：

```text
js/
  core/                // 启动、状态容器、运行时、通用客户端
  companion/           // 主场景、对话、presence、环境表达
  spaces/
    today/
    outbox/
    memory/
    privacy/
  domains/
    life-flow/
      tasks/
      routines/
      activities/
      diary/
      reminders/
      calendar/
  productization/      // PWA、路由、草稿恢复、更新
  adapters/            // API / fixture / 白名单转换
  services/            // 纯请求封装
  shared/              // 时间、校验、错误、操作门禁
```

### 4.2 现有模块归位

现阶段可先保持代码不大搬家，但按这个语义解释已有文件：

- `main.js`：composition root，只负责装配
- `app-state.js`：集中状态容器
- `life-flow-controller.js`：Today 和二级能力的总控制面
- `silent-spaces-controller.js`：来信、记忆、隐私
- `pwa-controller.js`：产品化底座
- `adapters/*`：接口白名单与契约归一化
- `services/*`：请求封装

### 4.3 迁移原则

- 先改产品层级，再改目录
- 先改入口优先级，再改文件归属
- 先保行为稳定，再做文件迁移
- 不为“看起来更模块化”而制造过多薄文件

## 5. 实施建议

1. 保持主场景和一级辅助空间的可见性优先。
2. Today 内部再容纳任务、日记、提醒、日历、活动、习惯等二级能力。
3. 功能不删除，只下沉，不抢首屏。
4. 新增代码优先落到产品语义明确的目录，而不是继续堆在同级文件下。
5. 后续联通前后端时，优先保证 adapter、state 和入口层级的稳定。

### 5.1 v1 当前落地状态

本轮已按上述原则完成首轮重构，后续前后端联通应以当前行为作为产品基线：

- `index.html` 中 Today、来信、记忆、隐私四个空间入口标记为一级辅助空间，继续保持首屏可达。
- Today 覆盖层先展示今日摘要和 Timeline；任务、习惯、活动、日记、提醒、日历等能力统一归入“更多生活流”。
- “更多生活流”默认收起，必须由用户显式展开；展开状态由 `today-view.js` 管理，并同步 `hidden` 与 `aria-expanded`。
- 二级能力仍使用原有 DOM、View、请求和状态逻辑，不删除功能，只改变入口优先级。
- 视觉调整沿用晶格温室的冷白、冰蓝、磨砂玻璃和光窗语言，相关样式集中在 `life-flow.css` 与 `crystal-solarium.css`。
- 当前实现保留按文件类型组织的顶层目录；产品能力边界先在 `js/features/life-flow/` 和现有控制面中稳定，物理目录迁移留到后续低风险批次。

实现与验收关联：

- 入口与 Today 标记：`apps/companion-web/companion-ui/index.html`
- Today 展开状态：`apps/companion-web/companion-ui/js/features/life-flow/today-view.js`
- DOM 绑定：`apps/companion-web/companion-ui/js/main.js`
- 视觉层级：`apps/companion-web/companion-ui/styles/life-flow.css`、`crystal-solarium.css`
- Chromium 浏览器回归：`rtk npm run test:browser`

## 6. 结论

这套产品现在的核心问题不是能力不足，而是层级需要更像“陪伴产品”。

正确方向是：

- 让主场景始终保有陪伴感
- 让 Today / 来信 / 记忆 / 隐私成为一级辅助空间
- 让任务 / 日记 / 日历等能力退到二级
- 让代码结构跟产品层级一致

这样既保留完整能力，又能把首发体验收束成一个更清楚的产品。
