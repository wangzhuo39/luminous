# Gemini API 输出边界与批次切分记录

> 状态：持续更新的工程经验基线
> 初版日期：2026-07-25
> 适用范围：Luminous 前端设计、实现与审查的无状态 Gemini API 调用

## 1. 结论

当前 Gemini 主/备端点不存在一个可依赖的固定输出上限。`max_tokens` 只是请求参数，不能证明服务端实际返回完整；HTTP 200 同样不能证明完成。

对当前前端代码生成任务，建议把一次响应设计为：

- **稳定目标：约 4.5–7 KB、120–200 行代码**；
- **可尝试区：约 7–10 KB**，必须有结束标记，且要接受重试或拆分；
- **高风险区：超过 10 KB 或同时输出两个中型文件**；
- **不作为计划依据：偶发的 15–24 KB 完整响应**。这类响应确实出现过，但不可重复，有时还包含大段上下文回显。

这不是模型的理论 token 上限，而是当前代理端点、模型、网络和响应封装共同作用下的**工程稳定区间**。更换模型后必须重新校准。

## 3. 强制完整性协议

每个实现请求必须指定唯一结束标记，例如：

```text
LUMINOUS_COMPLETE_S3_TODAY_VIEW_JS
```

调用记录器必须使用：

```bash
--expect-suffix LUMINOUS_COMPLETE_S3_TODAY_VIEW_JS
```

接受条件同时满足：

1. API/辅助脚本退出成功；
2. response 去除末尾空白后以指定标记结束；
3. 输出的所有目标文件或片段均闭合；
4. Codex 审查确认没有用回显的上下文冒充新代码；
5. 落盘后通过语法、导入和相关测试。

只满足 HTTP 200、只出现 code fence，或者代码“看起来差不多结束”都不能接受。

## 4. 批次大小策略

### 4.1 默认批次

优先让一次调用完成一个可独立验证的中型交付物：

- 一个 120–200 行 JS 文件；
- 一个 150–250 行 CSS 文件；
- 一个 HTML fragment；
- 一个 100–180 行表驱动测试文件；
- 2–3 个很短且紧密相关的文件，预估总输出仍不超过约 7 KB。

输入上下文可以比输出大。必要源码必须用 `--context-file` 原样拼入 request；不能只告诉 Gemini 一个本地路径。

### 4.2 必须拆分的情况

出现以下任一条件，应在调用前按自然边界拆分：

- 预计输出超过 250–300 行代码；
- 同时要求两个中型完整文件；
- 一个文件包含三个以上可独立实现的数据域；
- 上一次已产生非空响应但未命中结束标记；
- Gemini 开始大段回显输入源码，挤占输出空间。

拆分以模块或领域为单位，而不是按几十行小函数碎片化。例如：

```text
Fixture DataSource
├── Foundation + Today + Task + Routine
├── Activity + Diary
└── Reminder + Calendar + Action
```

最终仍可由 Codex 审查后组装为一个工程文件，不必为了调用拆分而污染代码架构。

### 4.3 不应过度拆分

API 按调用次数计费，因此不要为以下内容单独调用：

- 单个导入路径或语法修正；
- 少量集成胶水；
- Codex 可以从真实契约直接判断的 method/path 修正；
- 单一测试断言补强；
- 格式化、命名或删除上下文回显。

这些由 Codex 在集成审查中完成，再运行回归。

- 最终四图多模态审查使用约 3k–4.5k 中文字合同，备用端点 attempt 2 成功。

### 结束标记的反引号误判

场景回答都以 `` `CRYSTAL_SCENE_SPEC_COMPLETE` `` 结束。记录器传入的
`--expect-suffix CRYSTAL_SCENE_SPEC_COMPLETE` 会在严格字符串比较时看到末尾反引号，
从而把完整回答误判为失败并重复调用。

后续做法：

1. 如果提示词容易让模型用 Markdown 包裹标记，校验可使用 `--expect-suffix '```'`，同时在 Codex 侧检查标记正文；
2. 更理想的是让记录器将末尾单反引号/代码围栏剥离后再比对；未修改记录器前，不要把这种情况归类为截断；
3. 发现连续回答长度相近、章节齐全、`finish_reason=stop` 且只差反引号时，停止继续付费重试，保留 trace 并写选择说明。

### 当前平衡点

对于“设计规格而非完整文件”的多模态请求，约 4,500–6,500 中文字的合同、最多
7,000–9,000 output tokens 是当前较稳定的平衡点。一次请求可以覆盖一个完整视觉域；不要把
场景世界与复杂内容面板重新塞回同一请求，也不需要切成每个选择器一次调用。

### B5 Activity 样本（2026-07-26）

## 5. 失败分类与处理

### A. 网络层空响应

表现：TLS/curl/HTTP 错误，`stdout_bytes = 0`。

处理：

1. 保持同一完整 prompt；
2. 由记录器在主、备端点间切换；
3. 最多通常 4 次；
4. 整次最终失败则删除 run 目录；
5. 不因网络空响应缩小设计范围。

### B. HTTP 成功但未命中结束标记

表现：`exit_code = 0`、有非空 stdout，但 suffix 不匹配。

处理：

1. 视为输出截断，不能落盘；
2. 不继续无脑增加 `max_tokens`；
3. 按文件或领域边界缩小预期输出；
4. 下一次请求仍包含完整必要上下文；
5. 失败 run 按约定删除。

### C. 完整但质量不合格

表现：命中结束标记，但有 API 幻觉、字段错误、回显源码、错误 wrapper 或不符合设计。

处理：

- 成功 trace 保留；
- Codex 可做无设计判断的最小集成修正；
- 涉及视觉或大范围业务判断时，把当前真实源码和精确问题交给 Gemini 局部重做；
- 所有修正必须重新测试或截图验收。

## 6. 并发调用

互不依赖、不会修改同一文件的任务可以并发，例如 View、Controller、HTML fragment。

但并发只解决等待时间，不改变每次输出上限。当前观察到并发时也会出现更多网络空响应，尚不足以证明因果关系，因此采用以下保守规则：

- 只并发真正独立的 2–3 个任务；
- 有上下文依赖的任务必须顺序执行，例如 CSS 必须接收已生成 HTML 的真实内容；
- 每条调用独立 trace、独立结束标记、独立重试；
- 并发失败后先判断是网络空响应还是截断，再决定原样重试或缩小输出。

```text

必须覆盖的行为与禁止项
输出格式与建议行数
唯一结束标记
```

## 8. 重新校准条件

以下变化发生后，更新本文样本和建议区间：

- 主或备用 model 更换；
- 代理服务改变输出限制或响应封装；
- 连续 5 次中型代码调用表现明显变化；
- 开始生成框架组件、长 SVG、长测试或多文件 diff；
- 新的记录器能够读取 provider 的 finish reason/usage。

重新校准时至少记录：请求目标、输出行数/字节数、是否命中 suffix、attempt、endpoint role、是否回显上下文和是否可实际落盘。
