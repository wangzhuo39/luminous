# 静态体验原型重构 S1：栖光的主场景

你是 Luminous 的前端主设计师与实现工程师。请在 `/home/wz/luminous` 中完成一次静态体验原型重构的第一步。

## 这一步真正要完成什么

请建立一个视觉上已经成立的“栖光”产品主场景：用户一打开页面，先感到有一位陪伴者在场，再看见可以停留、回应和开口的空间。

本阶段只验收静态体验与前端结构，不验收后端联通。不要把目标做成“接口都调通”的页面，也不要把功能列表堆进首屏。

具体的 HTML、CSS、JavaScript 组织、布局方式和动效表达由你自行决定。你可以重写当前 `apps/companion-web/companion-ui/` 中的前端实现；不要继承或修补旧页面的构图包袱。

## 产品与视觉方向

产品是泛化的情感陪伴 AI，不绑定圣经、天平等特定角色道具。主方向为“晶格温室”：清澈、安静、有温度的陪伴空间，不是仪表盘、工作台、普通聊天工具或营销落地页。

首屏必须同时成立：

1. 人物主体图是第一视线信号，具有真实存在感；
2. 空间有远景、中景、前景和可呼吸的层次，但不依赖装饰性光球或渐变；
3. 用户能看见一段自然的默认回应，并知道自己可以在何处开口；
4. 输入区、回应区、人物不能互相遮挡；回应的阅读顺序必须在输入之前；
5. 页面看起来像可长期停留的陪伴空间，而非一张角色海报。

人物参考图：`docs/front_design/assets/companion_reference.png`。请把它作为主场景的真实内容使用，而不是占位符。

## 本阶段范围

请完成一个可以本地浏览的高保真静态原型，包括：

- 主场景的默认陪伴状态；
- 一段默认对话状态，包含用户说过的话与陪伴者回应；
- 一个安静、非工具化的“今天”入口；
- 一处低打扰的来信/主动联系入口；
- 一处记忆与隐私的入口暗示。

这些入口可以进行纯前端的本地状态切换或展开，以展示空间关系和内容层级，但不需要完成真实业务操作。不要在这一阶段实现任务、提醒、日程、记忆、设置的 CRUD。

## 数据与后续联通边界

本阶段禁止调用任何 `/api/*` 接口，也不要使用 `fetch` 假装接入后端。

请使用清晰、独立的默认数据/fixture 来驱动场景和各个展示状态，并让渲染层只依赖稳定的前端展示模型。后续工程师将把真实后端响应转换为这些展示模型，因此不要让视觉组件直接耦合 HTTP 响应字段。

数据结构和模块划分由你自行决定，但需要让以下概念有明确的展示边界：

- 场景与陪伴状态；
- 对话记录与输入草稿；
- 今日摘要；
- 来信摘要；
- 记忆/隐私入口状态。

## 约束

- 只编辑 `apps/companion-web/companion-ui/`，以及确有必要的直接前端资源；不要编辑后端、`.env`、部署文件或 Git 配置。
- 不使用侧边栏、卡片墙、通用聊天气泡、装饰性光球或渐变背景。
- 不显示任何内部思考、prompt、ledger、trace、jobs、导出或调试内容。
- 使用语义化 HTML、键盘可达控件、可见焦点和 `prefers-reduced-motion`。
- 以桌面和 390x844 手机视口为一等目标；移动端键盘与底部安全区不得遮住输入或最新回应。
- 不将截图、调试文件或临时产物放进 `companion-ui/` 的产品静态资源目录。
