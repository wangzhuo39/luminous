我看完你这份实现记录后，结论比较明确：

> **现在的 Android 方案不是“走错路线”，但确实包含几处不适合作为长期生产架构的设计。**
>
> `STT + LLM + TTS` 本身没有问题。真正需要重构的是 **Android 实时音频层和会话编排层**。

我会把当前方案评价为：**MVP 架构合理，生产级实时通话架构还不够合理。**

### 当前哪些东西是对的

| 当前设计                                      | 评价         | 原因                        |
| ----------------------------------------- | ---------- | ------------------------- |
| `AudioRecord → 16k mono PCM`              | ✅ 对        | ASR 实时输入很合适               |
| 100ms PCM 持续采集                            | 🟡 可用      | MVP 可以，低延迟可继续缩短           |
| 本地 VAD                                    | ✅ 对        | 应该在端侧尽快知道用户开始说话           |
| pre-roll                                  | ✅ 思路对      | 防止 VAD 把用户第一个字吃掉          |
| 长连接 WebSocket                             | ✅ 可行       | AI Voice Agent 完全可以这么做    |
| STT → LLM → TTS                           | ✅ 对        | 模块化、可控，非常适合 Companion     |
| `response.cancel` 打断                      | ✅ 很重要      | 已经具备 barge-in 基础          |
| AI 说话时仍检测用户                               | ✅ 对        | 是全双工体验的基础                 |
| TTS PCM → Base64 → WebView → AudioContext | 🔴 不推荐长期保留 | 媒体数据不应该来回跨 Native/WebView |
| 每轮重新建立上游 ASR WebSocket                    | 🟠 建议改     | 增加 turn 启动复杂度和延迟          |
| 固定振幅阈值 VAD + 固定 900ms                     | 🟠 MVP 方案  | 不等于真正的 turn detection     |
| 最大 5 秒 pre-roll                           | 🟠 太激进     | 已经实际导致过协议问题               |
| 网络错误直接结束整场通话                              | 🔴 不合理     | 手机网络抖动很正常                 |
| 无 Foreground Service / Audio Focus / 蓝牙管理 | 🔴 生产版必须解决 | Android 通话生命周期不完整         |

这些判断对应你文档里描述的真实实现，而不是猜测。比如现在 Native 收到 TTS binary 后会**转 Base64 再派发给 WebView**，WebView 再负责 AudioContext 播放。

## 我认为当前最大的架构问题：音频“跨层”太多

现在大概是：

```text
麦克风
 ↓
Android Native AudioRecord
 ↓
Native VAD
 ↓
Native WebSocket
 ↓
服务器
 ↓
TTS PCM
 ↓
Native WebSocket
 ↓
Native
 ↓
PCM → Base64
 ↓
Capacitor notifyListeners
 ↓
WebView Javascript
 ↓
Base64 → PCM
 ↓
AudioContext
 ↓
扬声器
```

这里前半部分还不错。

真正奇怪的是后半部分：

```text
TTS PCM
 ↓
Native
 ↓
Base64
 ↓
JS
 ↓
AudioContext
```

**这是我最建议重构的地方。**

因为既然实时音频采集已经放 Native 了，实时播放最好也放 Native：

```text
                 Android Native Call Engine
                         │
             ┌───────────┴────────────┐
             ↓                        ↓
        AudioRecord               AudioTrack
             ↓                        ↑
        Mic PCM                    TTS PCM
             ↓                        ↑
             └────── WebSocket ───────┘
```

WebView 只负责：

```text
UI
字幕
通话按钮
状态动画
聊天内容
```

不要负责高频实时 PCM。

也就是形成非常清楚的职责：

```text
Native
= 音频实时系统

WebView
= UI

Server
= AI
```

这会比：

```text
Native
= 一半音频

WebView
= 另一半音频 + UI
```

干净很多。

而且你当前文档已经明确说 WebView 生命周期会影响整个通话，后台/销毁时没有通话级恢复。

# 第二个问题：现在的 Turn 建连方式不够漂亮

你现在是：

```text
VAD speech_start
 ↓
JS发送 turn.start
 ↓
服务器建立 ASR WebSocket
 ↓
服务器返回 turn.ready
 ↓
Android 才开始发送音频
 ↓
之前的音频靠 pre-roll 补回来
```

文档实际上就是这个流程。

这导致你必须设计：

```text
speech_start
↓
等网络
↓
等服务器
↓
等 ASR
↓
期间先缓存 PCM
```

于是才有了：

```text
callPreRoll
最大 5 秒
```

最后第一次实机就出现：

```text
5 秒 × 16k × 2 bytes
≈ 160 KB
```

一次性 WebSocket frame 超过服务器 64 KB 上限。你现在通过 48 KB 分片修掉了这个 bug。

**48 KB 分片这个修复是正确的，但它修的是症状。**

更理想的架构是：

```text
通话开始
 ↓
建立 realtime session
 ↓
ASR runtime 准备好
 ↓
保持准备状态

用户开始说
 ↓
PCM立即进入流
```

如果上游 ASR 支持，就进一步：

```text
Call Session
      ↓
Persistent ASR Session
      ↓
turn 1
reset
turn 2
reset
turn 3
...
```

而不是：

```text
每说一句话：
connect ASR
→ speech
→ disconnect

下一句话：
connect ASR
→ speech
→ disconnect
```

这样 pre-roll 只需要做它真正应该做的事情：

> **补 VAD 判断之前的几百毫秒声音。**

而不是：

> “网络/ASR 还没 ready，所以最多替我缓存五秒。”

这是两个完全不同的概念。

# 第三个问题：当前 VAD 其实只是 MVP VAD

现在是：

```text
平均绝对振幅
threshold = 450

连续两个 voiced frame
→ speech_start

连续 900ms silence
→ speech_end
```

这是非常简单的能量阈值 VAD。

不是说不能用。

第一版非常适合。

但最终 Companion 不应该让它直接决定：

> **用户说完了。**

因为：

```text
“我今天其实……”

停 1 秒

“心情特别不好。”
```

当前逻辑很容易：

```text
900ms
↓
speech_end
↓
LLM 开始回答
```

但实际上用户根本没讲完。

长期应该拆成：

```text
Audio
 ↓
Neural VAD
 ↓
有没有人在说话？
 ↓
Endpoint / Turn Detector
 ↓
这个人真的讲完了吗？
```

也就是：

> **VAD 判断“有没有声音”。**
>
> **Turn Detection 判断“轮到 AI 了吗”。**

这对 Companion 的体验影响非常大。

# 第四个问题：掉线直接挂电话是不合理的

目前：

```text
WebSocket error
或者
closed
 ↓
close()
 ↓
停录音
关 WebSocket
关 AudioContext
state = idle
```

这在你文档里已经明确记录。

而手机网络天然会发生：

```text
Wi-Fi → 5G
5G → Wi-Fi
弱网
短暂断流
VPN变化
基站切换
后台/前台切换
```

所以应该有：

```text
CONNECTED
 ↓
短暂断开
 ↓
RECONNECTING
 ↓
恢复 call_id
 ↓
继续通话
```

例如：

```text
call_id = A82F
turn_id = 17
audio_seq = 8291
```

连接回来告诉服务器：

```text
resume call A82F
```

而不是重新创建一个“陌生的新通话”。

你文档自己也把自动重连、turn 恢复、播放队列恢复列为了尚未解决的问题。

所以这里不是模型问题，而是 **Realtime Session Engine** 还没建立起来。

# 第五个问题：Android Native Call Engine 现在还不完整

你文档里这个判断是准确的：

目前没有独立的：

```text
Foreground Service
Audio Focus
Bluetooth routing
锁屏保持
后台生命周期
```



如果希望：

> 锁屏还能通话
> 切到微信还能继续说
> 插入蓝牙耳机自动切换
> 来电话时正确暂停
> 音乐 App 和你抢声音时正确处理

这些都必须补。

Android 官方为持续可感知后台工作提供 Foreground Service；涉及后台麦克风时尤其需要遵守对应的 microphone foreground-service 类型和系统限制。([Android Developers][1])

Android 也提供专门的 communication-device API 来管理语音通话的扬声器、耳机、蓝牙等路由，现代 Android 推荐使用 `setCommunicationDevice()` 体系。([Android Developers][2])

而你现在已经用到 Android 的 `AcousticEchoCanceler` / Noise Suppressor 思路，这是正确方向：AEC 的目的正是从麦克风捕获信号里消除远端扬声器回放造成的回声。([Android Developers][3])

# 我给当前 Android 方案的判断

如果按照“是否要推倒重做”来看：

**不用推倒。**

核心服务架构：

```text
Android
 ↓
Realtime Server
 ↓
STT + Companion LLM + TTS
```

继续保留。

但是我会明确要求开发人员逐步把：

```text
AudioRecord Native
+
Base64 WebView AudioContext
+
简单 VAD
+
每 turn 建 ASR
+
掉线即挂断
```

演进成：

```text
Native Call Engine
+
Native AudioRecord / AudioTrack
+
Neural VAD + Turn Detection
+
Call-level realtime session
+
persistent/ready ASR
+
streaming LLM
+
streaming TTS
+
barge-in
+
session reconnect/resume
```

### 优先顺序我会这样排

**P0：先确认现在 48 KB 分片修复后的实机“两轮连续通话”稳定。**你们文档本身也把这件事列为下一步第一优先级。

**P1：把 TTS 播放从 WebView AudioContext 移进 Native。**

这是我认为当前最值得做的架构调整。

**P2：把 Native Audio 层升级成真正的 `CallEngine`，补 Audio Focus、设备路由和 Foreground Service。**

**P3：升级 VAD / Turn Detection，缩短 pre-roll，不再让 900ms silence 直接代表“用户说完”。**

**P4：Call-level reconnect/resume。**

**P5：最后才决定 WebSocket 是否需要换 WebRTC。**

所以如果有人现在跟你说：

> “因为你用了 Capacitor/WebSocket/STT+LLM+TTS，所以整个 Android 实现路线都错了。”

我不会同意。

真正准确的描述是：

> **AI 架构是对的，Android realtime media architecture 目前还是 MVP 级；最明显的技术债是 Native/WebView 混合音频链路，以及缺少真正的 Call Session / Turn / Lifecycle 层。**

这才是我认为你这份实现记录暴露出的核心问题。
